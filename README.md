# Vending Machine

> A terminal vending machine: list the products, see what your coins can buy, buy one and get your change. The machine remembers every sale: stock goes down and the coins it holds are updated.

Group project for *Software Development for Business* (ESADE, 2026–27).

## Install

You need [uv](https://docs.astral.sh/uv/getting-started/installation/). It installs Python 3.13 for you.

```
git clone https://github.com/esade-swdev-2026/vending-machine.git
cd vending-machine
uv sync
```

`uv sync` creates a virtual environment (`.venv`) and installs the exact versions pinned
in `uv.lock`, so every teammate and CI get the same ones. When you change a dependency in
`pyproject.toml`, run `uv lock` and commit the updated `uv.lock`; CI fails if the two disagree.

## Run

Run every command from the repository root, so the default data files in `data/` are found.

```
uv run vending-machine --help
```

### See every product

```
$ uv run vending-machine products
  1  Choco bons      1.50 €
  2  KitKat          1.30 €
  3  Kinder Bueno    SOLD OUT
  4  Water           1.00 €
  5  Coca-Cola       2.00 €
```

### See what your coins can buy

```
$ uv run vending-machine affordable 100 50
Credit: 1.50 €
  1  Choco bons      1.50 €
  2  KitKat          1.30 €
  4  Water           1.00 €
```

### Buy a product

`buy SLOT COINS...`: buy the KitKat in slot 2 with a 2 € coin:

```
$ uv run vending-machine buy 2 200
Enjoy your KitKat!
Change: 1 x 0.50 € + 1 x 0.20 €
```

Coins are given **in cents**, separated by spaces (`100 50 50` is 1 € + 50c + 50c).
Accepted coins: `200, 100, 50, 20, 10, 5, 2, 1`.

How the change is made:
- The machine first adds the coins you inserted to the coins it already holds, so it can give some of your own coins back as change.
- It pays with the largest coins first. If that leaves an amount it can't pay, it uses one big coin fewer and tries again with smaller ones. With one 50c and three 20c, 60c of change is paid as 3 x 20c.

**`buy` saves the machine after each sale.** The product's quantity in `data/products.csv`
goes down by one, and `data/machine_coins_change.csv` gets the inserted coins and loses the change.
After 5 KitKat sales, `products` shows `SOLD OUT` for slot 2. A failed sale (any error below) saves nothing.
To reset the sample data, run `git checkout data/`.

### Owner: restock a slot

`restock SLOT UNITS`: put 10 Kinder Bueno back in slot 3:

```
$ uv run vending-machine restock 3 10
Slot 3: Kinder Bueno now has 10 units.
```

### Owner: see which slots need a refill

```text
$ uv run vending-machine refill
1 slot(s) to refill:
  3  Kinder Bueno    SOLD OUT
```

### Owner: view session revenue

The machine tracks the revenue generated by successful purchases during the current session.

```text
$ uv run vending-machine revenue
Current session revenue: 1.30 €
```

Revenue is calculated using the selling price of each purchased product, not the total amount of coins inserted. Failed purchases do not increase revenue.

The counter is saved in `data/revenue.csv`, so it persists between program executions.

### Owner: start a new session

To reset the revenue counter to zero:

```text
$ uv run vending-machine start-session
New session started. Revenue: 0.00 €
```

Starting a new session resets only the revenue counter. Product quantities and the machine's available coins remain unchanged.

The counter then accumulates revenue from subsequent successful purchases.

### Options

| option | commands | default | meaning |
|---|---|---|---|
| `--stock PATH` | `products`, `affordable`, `buy`, `restock`, `refill` | `data/products.csv` | The products CSV file |
| `--coins-file PATH` | `buy`, `restock` | `data/machine_coins_change.csv` | The coins available for change |
| `--revenue-file PATH` | `buy`, `restock`, `revenue`, `start-session` | `data/revenue.csv` | The session revenue CSV file |

## Run with Docker

Docker lets you run the vending machine without installing its Python dependencies directly on your computer.

From the repository root, build the Docker image:

```bash
docker build -t vending-machine .
```
To list the available products using Docker:

```bash
docker run --rm vending-machine products
```
To keep product quantities, coins, and session revenue between separate Docker runs, use a named volume mounted at `/app/data`:

```bash
docker run --rm -v vending-machine-data:/app/data vending-machine products
```
To buy a product using the persistent volume:

```bash
docker run --rm -v vending-machine-data:/app/data vending-machine buy 2 200
```
To verify that the revenue persists, start another container using the same volume:

```bash
docker run --rm -v vending-machine-data:/app/data vending-machine revenue
```

On fresh machine data, a successful purchase of slot 2 generates 1.30 € in session revenue. The second container reads the updated revenue from the shared volume.


### Pull the published image from GHCR

Our release pipeline publishes the `v1.0` image to GitHub Container Registry (GHCR), so you can download it instead of building it locally.
The package is private, so log in first with a GitHub token that has the `read:packages` scope:

```bash
docker login ghcr.io -u <your-github-username>
docker pull ghcr.io/esade-swdev-2026/vending-machine:v1.0
```

To use the downloaded image with the existing Docker commands, tag it as `vending-machine:latest`:

```bash
docker tag ghcr.io/esade-swdev-2026/vending-machine:v1.0 vending-machine:latest
```

## Errors

Bad input never shows a traceback: it prints `Error: ...` and exits with code 1.

| problem                              | example                                               | message                                                     |
|--------------------------------------|-------------------------------------------------------|-------------------------------------------------------------|
| unknown slot                         | `uv run vending-machine buy 99 200`                   | `Error: No product in slot 99.`                             |
| sold-out product                     | `uv run vending-machine buy 3 200`                    | `Error: Kinder Bueno is sold out.`                          |
| coin that is not accepted            | `uv run vending-machine buy 1 3`                      | `Error: Coin 3 is not accepted.`                            |
| not enough money                     | `uv run vending-machine buy 1 100`                    | `Error: Choco bons costs 150 cents, you inserted 100.`      |
| the machine cannot make the change   | (when its coins run out)                              | `Error: Cannot give 70 cents of change.`                    |
| missing data file                    | `uv run vending-machine products --stock missing.csv` | `Error: missing.csv not found. Run from the repository root.` |
| bad row in a data file               | (e.g. a price that is not a number)                   | `Error: data/products.csv: bad product on line 3.`          |
| the same slot twice in the CSV       | (two rows with slot `1`)                              | `Error: data/products.csv: slot 1 is repeated on line 3.`   |
| price of 0 or less in the CSV        | (a row with `price_cents` = `-50`)                    | `Error: data/products.csv: price must be more than 0 on line 2.` |
| negative quantity in the CSV         | (a row with `quantity` = `-3`)                        | `Error: data/products.csv: quantity cannot be negative on line 2.` |
| unknown coin in the coin file        | (a row with `coin_cents` = `3`)                       | `Error: data/machine_coins_change.csv: coin 3 is not accepted on line 2.` |
| restock 0 units or fewer             | `uv run vending-machine restock 3 0`                  | `Error: Restock at least 1 unit.`                           |
| restock above the slot's capacity    | `uv run vending-machine restock 1 50`                 | `Error: Slot 1 holds at most 20 units; it has 10.`          |
| bad revenue file                     | (two rows, or a negative total)                       | `Error: data/revenue.csv: expected exactly one revenue row.` |

## Data files

`data/products.csv`, one product per row (each slot only once):

| column        | meaning                          |
|---------------|----------------------------------|
| `slot`        | slot number (integer)            |
| `name`        | product name                     |
| `price_cents` | price in cents (integer, more than 0)      |
| `quantity`    | units left (0 or more); `0` shows SOLD OUT |


`data/machine_coins_change.csv`, the coins the machine holds to give change:

| column       | meaning                        |
|--------------|--------------------------------|
| `coin_cents` | coin value in cents            |
| `count`      | how many of that coin it holds |

`data/revenue.csv`, the revenue of the current session (one row):

| column          | meaning                                    |
|-----------------|--------------------------------------------|
| `revenue_cents` | revenue since the last `start-session`, in cents (0 or more). A missing file counts as 0 |

## Checks

The script `scripts/check.sh` runs the same four checks as CI (GitHub Actions,
`.github/workflows/check.yml`), in the same order, and stops at the first one that fails.
Run it from the repository root before every commit and push. If it passes here, CI passes.

```
bash scripts/check.sh
```

It works in any bash terminal: Linux, macOS, WSL, or Git Bash on Windows. It runs:

```
uv run ruff check .            # lint
uv run ruff format --check .   # formatting (fails if a file is not formatted)
uv run mypy src tests          # types
uv run pytest                  # tests
```

Without bash, run those four commands one by one. If the formatting check fails, run
`uv run ruff format .` once to fix every file, then commit.

The tests never touch the real `data/` files: the command-line tests work on copies in a temporary folder.

## How it works

The machine is plain data, and a sale is a function from the machine before to the machine after:

- `MachineState` (a frozen dataclass) holds `products` (`{slot: Product}`) and `coin_float` (`{coin_cents: count}`).
- `sell(state, slot, coins)` checks the sale, makes the change and returns a `SaleResult`: the `Sale` (product and change) and the **new** `MachineState`. It never changes the state it was given.
- `cli.py` reads the state from the CSVs, calls `sell`, saves the new state and prints the result.

## Project layout

```
src/vending_machine/
  models.py       Product, Sale, MachineState, SaleResult, the Coins/Products types,
                  the accepted coins and the error classes (no I/O)
  inventory.py    find_product, affordable_products, empty_slots, restock_slot (pure)
  payment.py      credit_from_coins, add_coins, remove_coins, make_change (pure)
  machine.py      sell: one whole purchase, old state in, new state out (pure)
  formatting.py   format_cents, format_change, format_product_lines (pure)
  storage.py      reads and writes the CSV data files (the only module that touches files)
  cli.py          the typer commands: read, call the pure functions, save, print
  __main__.py     lets `python -m vending_machine` work
data/           sample products.csv, machine_coins_change.csv and revenue.csv
scripts/check.sh  runs the four CI checks locally
tests/            pytest tests, one file per module in src/
pyproject.toml    dependencies and tool settings
```

## Use of AI

We used AI assistants (mainly Claude, plus ChatGPT now and then) as a second pair of eyes,
not as the author of the project. The design of the machine, the split into modules
(`inventory`, `payment`, `storage`, `cli`), the data files and the business rules
(slot capacity, exact change, the session revenue counter) were decided by the group
in class and in our own meetings. The AI helped with small, well-scoped tasks around that work:

- **Code revision.** Before opening a pull request, some of us pasted our diff and asked
  "what could go wrong here?". This is how we noticed, for example, that `restock_slot`
  added the restocked units twice, and that `read_state` and `cli.py` each had their own
  default path for the revenue file. The AI pointed at the problem; we wrote the fix and
  the test that proves it ourselves.
- **Edge cases for tests.** We asked for lists of inputs that could break a function
  (an empty CSV, a negative price, a slot that doesn't exist, paying with too few coins).
  We kept the ones that made sense for our rules, wrote the `pytest` tests by hand and
  threw away the rest.
- **Understanding tool errors.** When `mypy`, `ruff` or GitHub Actions failed with a message
  we didn't understand, we asked the AI to explain it in plain words before fixing it.
  It also helped us spot why Docker was ignoring our `.dockerignore` (the file name started
  with a space).
- **Wording.** Rephrasing a few error messages, the `--help` text of the CLI commands,
  and some sentences of this README so they are short and clear.
- **Checking against the rubric.** At each checkpoint we asked it to compare our repository
  with the lab instructions and list anything we had missed. We then decided as a group
  what to do and who would do it.

What the AI did **not** do:

- **It did not commit, push, merge or review anything.** Every commit in the history was
  written and pushed by a member of the group from their own account. Every pull request
  was opened by a member, reviewed by a different member (or by our partner group),
  and squash-merged by a member after the review comments were answered.
- **It did not get the last word.** Suggestions were only kept after we had read them,
  run `bash scripts/check.sh` (tests, `ruff`, `mypy`) and, for the Docker part, built and
  run the image ourselves. Several suggestions were rejected because they were too complex
  for what the brief asks or did not fit our design.

Each of us can open any file in this repository and explain what every function does,
why it is written that way, and how it is tested. If something in the code was suggested
by an AI, we understood it well enough to rewrite it in our own words before it was merged.
